Abliteration

Abliteration removes the refusal direction from a model’s internal vectors by editing its weights, without training. In most of the models studied, refusals became far rarer afterwards, but the effect depends on the model and on how much of it is edited.

Where refusals come from and where to look for them

  • Refusal. A model learns to refuse in post-training, the stage that follows pretraining (see “Training”). Its tendency to refuse is therefore stored in its weights. Filters that providers place around a model are a separate layer, and abliteration does not touch them.
  • The question. If refusal is in the weights, where exactly, and can it be removed from there without training? Arditi et al. (2024) tested this on 13 open-weight models of up to 72 billion parameters.
  • The token’s vector. For every token in the context the model keeps one vector, which passes through all the layers. It starts as the token’s embedding. Each layer reads this vector and adds its output to it instead of replacing it with a new one, so the vector has different values after each layer. The literature calls this vector the residual stream (see “Vectors and matrices”). A phrase such as “the residual stream after layer 12” refers to its values at that point. Here we call it “the token’s vector”. In Llama 3 8B it has 4096 coordinates. A layer has two blocks: attention brings in information from the vectors of earlier tokens, and a neural network called an MLP computes its output from that one token’s vector alone.
  • A direction. The token’s vector is a single list of numbers, with no separate fields for separate pieces of information. A single coordinate usually has no meaning of its own (see “Vectors and matrices”): information is stored across many coordinates at once, in particular proportions. A direction describes such proportions. It is a separate vector with the same number of coordinates, not a part of the token’s vector. Only its proportions matter, not its length, so its length is set to 1. We look for a direction associated with the model’s refusal behaviour.
  • A component. Every vector can be split into two parts: the component along a chosen direction and the part perpendicular to that direction. The component is the direction multiplied by one number, which says how much of the direction the vector contains. Because the direction has length 1, that number is the dot product: multiply the matching coordinates of the two vectors and add up the results. For the vector x = (25, 0) and the direction r = (0.6, 0.8) the dot product is 25·0.6 + 0·0.8 = 15, the component is 15·r = (9, 12), and the perpendicular part is (25, 0) − (9, 12) = (16, −12). Its dot product with r is 16·0.6 − 12·0.8 = 0, which is what perpendicular means. Removing a direction from a vector means subtracting the vector’s component along that direction. The perpendicular part does not change. Components along other directions that are not perpendicular to the removed one change too.
  • The answer. In the models studied, refusal depended largely on one such direction. Abliteration has three stages: find that direction, test it, and remove it from the weights. The widget shows them in order.

Follow how a refusal direction is found, tested and removed

A schematic drawing in two dimensions: the positions are invented, not measured in a model, and real vectors have thousands of coordinates. No request text is shown, and the drawing predicts no refusal rate.

Stage 1. Find the direction

  • Data. Arditi et al. gave each model 128 harmful requests and 128 harmless ones. Only the requests are needed, with no example answers.
  • Where it is measured. After every layer they read the vectors of the last tokens of the prompt, i.e. the chat-template markers that follow the user’s message (see “How a model sees a chat”). At that point the model has read the whole request but has not started answering.
  • Candidates. The average vector for harmful requests minus the average vector for harmless ones is a candidate refusal direction. The number of candidates is the number of layers multiplied by the number of markers being measured.

Stage 2. Test the direction

  • Correlation. A difference of averages shows only correlation, because the two groups of requests can also differ in topic or length. So each candidate is tested in a running model, on requests other than the ones it was computed from.
  • Two tests. In the first, the candidate, i.e. the difference of averages (not yet scaled), is added to the vector of every token in the context, after one chosen layer only. The model should then start refusing harmless requests. In the second, the component along the candidate is subtracted from the vector of every token in the context: after the embedding and after every attention and MLP block. The weights are not changed. The model should stop refusing harmful requests, while its answers to harmless ones barely change.
  • Selection. The candidate chosen is the one that passes both tests and reduces refusals the most. We scale it to length 1 and call it r. In the study by Arditi et al., one such direction was enough for the whole model. It was computed from measurements after a single layer, and the component along it was subtracted after every block, because all blocks read and change the token’s vector in the same coordinates.

Stage 3. Remove the direction

  • Names. Removing the direction while the model runs is called directional ablation, and removing it from the weights is called weight orthogonalisation. “Abliteration” blends “ablation” (switching off part of a model to see what it did) and “obliterate”. It refers to the weight edit and shows up in model names as the suffix “abliterated”.
  • In the weights. The second test changes vectors during the computation, so it needs access to the inside of a running model. The same effect can be stored in the weights. In a typical transformer, the token’s vector is the sum of the embedding and the outputs of all the attention and MLP blocks. The last step of every block is multiplication by a matrix and addition of a constant vector, the bias. If none of those steps can produce an output with a component along r, the sum has no such component either, after any layer.
  • The formula. Multiplying a matrix by a vector gives a sum of the matrix’s columns, each multiplied by a coordinate of the vector. So it is enough to remove the component along r from every column. The formula does that: every matrix W whose output goes into the token’s vector is replaced with W − r (rᵀW). Here rᵀ is the vector r written as a row, and rᵀW is a row of numbers, one for each column of W: the dot product of r with that column. Multiplying r by that row gives a matrix in which each column is the component along r of the matching column of W. Once it is subtracted, no output of the new matrix has a component along r.
  • Which matrices. The edit covers the matrices that write into the token’s vector, meaning those whose output is added to it: the embedding table and the output matrix of every attention and MLP block. The component along r is subtracted from the biases of those blocks. Other architectures can have additional matrices that write into the token’s vector, such as a separate positional embedding. The other matrices only read the token’s vector and stay unchanged. One of them is the vocabulary matrix, which turns the final vector into logits, the scores used to calculate probabilities for the next token. If the model shares it with the embedding table, it changes along with that table.
  • Equivalence. Arditi et al. prove equivalence of the token-vector computation: for the same input tokens, editing every writing matrix and its bias gives the same vector after each block as removing the component after the embedding and after every block. Saving the weights to a file introduces only differences due to rounding. If the edit also changes a shared vocabulary matrix, the logits can differ as well. Editing only some of the matrices can also reduce refusals, but its effect has to be measured on the edited model.
  • The result. The edited weights are saved in an ordinary file: the model is the same size and runs as fast as the original. Preparing it takes a few hundred requests run through the model and a recalculation of the matrices, with no gradients and no examples of harmful answers. The direction is computed for specific weights, so for a new version of the model it has to be found again. Quantisation after the edit (see “Quantisation”) changes the weights again, so refusals have to be measured once more.
  • MoE models. In MoE models there are many experts in place of one MLP block, and a router picks a few of them for each token (see “Mixture of Experts”). Every expert writes into the token’s vector. Shi et al. (a preprint from the company Continuum AI, September 2026) split the block output matrices of GLM-5.3-Flash, a 320-billion-parameter model, into three groups: attention, the experts picked by the router, and the remaining MLP outputs. They removed the direction in a running model, without changing the weights, from the outputs of one, two or all three groups. The original model refused 95% of 256 requests. After removal from one group, it refused 80–93% of requests; after removal from two groups, 41–88%; and after removal from all three groups, 17%. This model’s weights are released in an 8-bit format. Rounding them back to 8 bits after the edit put part of the removed component back.

What the edited model does

  • Refusals. In the studies by Arditi et al. (2024) and Shi et al. (2026), edited models refused far less often, but did not stop entirely. In the study by Arditi et al., all 13 models refused nearly every harmful request and answered most of them once the direction was removed. HarmBench is a set of harmful requests used for testing models. In a separate measurement on 150 requests from that set, GLM-5.3-Flash refused 17% after a weight edit, compared with 92% before the edit. In such studies a refusal is recognised by typical phrases in the answer or judged by a second model.
  • What the answers contain. A model can answer without refusing and still produce harmless content, so Arditi et al. measure refusals and harmful answers separately. On HarmBench, a classifier judged 79% of the edited Qwen 7B’s answers harmful, against 7% before the edit. They tested the effect of a system prompt on only two model families from 2023, Llama-2 and Qwen, and it depended on the family. The studies cited here have no newer measurement of that effect.
  • Other answers. The edit changes answers unrelated to refusal as well, because later blocks used to read a component that is no longer there. In the study by Arditi et al., most benchmark scores barely moved. On TruthfulQA, a test of questions that people commonly answer incorrectly, scores fell by 1 to 6 percentage points for all 13 models. So check an edited model on your own task like any new model (see “Evals”).
  • Outside the model. The edit changes only the weights. It gives the model no new knowledge and leaves alone the safeguards that sit outside the model: classifiers at the API provider, rate limits and tool permissions. If you run the model yourself, you have only the safeguards you put in place.

Limits of the method

  • One direction. Describing refusal with a single direction is an approximation. Arditi et al. call their result an existence proof for such a direction, not a study of how best to find it. Wollschläger et al. (ICML 2025) found several independent refusal directions. In the study by Shi et al. (2026), GLM-5.3-Flash still refused 20–47% of requests about violence, sexual content and hate with 1 to 12 directions removed at once. So “abliterated” in a model’s name says only that a refusal direction was removed. It does not say from how many matrices, and it does not guarantee that the model answers everything.
  • Different models. Hadetskyi et al. (a preprint from the company Cracken AI, July 2026) applied the same procedure to 24 open-weight models, from 0.6 billion to 1 trillion parameters: they computed the direction from cybersecurity requests and changed at most 30% of the layers. After the edit, 12 models refused substantially less often in that domain, 7 showed a partial effect, and 5 showed almost no effect, regardless of model size. According to the authors, a model from that last group, such as Mistral Large, refuses less often when other abliteration tools are used, but in every domain at once.
  • One domain. The direction depends on the requests it is computed from, so the edit can be aimed at one domain. The reduction is rarely confined to that domain: in the same study refusals usually fell in other domains too, and the authors name only two of the 24 models, Kimi K2 and Gemma 12B, as cases of pronounced domain selectivity. Kimi K2, a 1-trillion-parameter model, refused 100% of the requests in each of six domains on the authors’ own test set before the edit. After the edit it refused 7% of the cybersecurity requests, and between 44% and 100% in the other five domains. On public benchmarks the drop for this model was smaller: from 88% to 51% in the cybercrime category. Refusals were detected by phrase matching.
  • Defence. Training can make refusals harder to remove with this method. Abu Shairah et al. (2025) fine-tuned small models (1.5 to 7 billion parameters) to refuse with a longer explanation. With one direction removed, these models still refused over 90% of harmful requests in that paper’s main test, against 14–21% for the same models without that training. The training itself lowered the score on MMLU, a general-knowledge test, by 0.6 to 1.3 percentage points.

What it means for your system

  • Who can do it. Anyone with access to the weights, which are available to download for open-weight models (see “Open-weight models”). It cannot be done through an ordinary API, which gives access to neither the weights nor the model’s internal computation. In 2024 Arditi et al. put the compute cost of editing a 70-billion-parameter model at less than $5, and noted that fine-tuning had already made it possible to reduce refusals. Ready-made edited copies are published, and some hosting services serve them through an API (as of November 2026). So an open-weight model’s refusals are a default setting that the holder of the weights can weaken considerably. Judge the risk of such a model by what it can do.
  • A downloaded model. The studies cited here describe no test that recognises an edited model from its answers alone. The advice that follows is not drawn from those studies. Compare the weight files with the official release, for example by checksum, because an edited copy has different weights. Any modification, including quantisation, changes the checksum, so a difference says only that the file is not the official one. For a model from another source, measure refusals on your own set of requests: that shows how it behaves, not where it came from.
  • Someone else’s model. An attacker does not need to break your model, because they can use their own. Hadetskyi et al. write that they need a model for authorised offensive security operations and that a model without refusals greatly widens what an agent can do on its own. A person acting without authorisation can use the same capabilities. So protect data and money with safeguards that work regardless of whether a model refuses: narrowly scoped API keys, spending limits with alerts, and tool permissions limited to what each tool needs.
  • An example. A report from the hosting platform Railway, dated 10 November 2026, describes an intrusion in October 2026 in which API keys for AI providers were stolen. According to the report, evidence indicates that the attacker “was using abliterated models with no safeguards, with the ability to perform escalated actions in rapid succession”. The report does not say which models these were or where they ran. Separately, the report estimates unauthorised spend on the stolen keys at about $740,000 and does not link that figure to the abliterated models.
