Agent identity

An agent calling tools has to prove who it is, and a shared API key can’t do that: it only shows that someone holds the key. SPIFFE gives each process a short-lived proof of identity, issued from where and how the process runs. It answers “who is calling”, but not “should they be”.

An SVID is a short-lived proof of identity issued through SPIFFE: a token or a certificate. Anyone who copies a token can use it. A certificate also needs a private key.

Why an API key isn’t an identity

  • A key is a bearer secret and doesn’t say who used it. When every agent replica and two other teams share the same key, the log only shows “key X”. Rotating it affects everyone at once, so rotation gets postponed and the key lives for months.
  • An agent is a worse keeper of secrets than an ordinary service, because the content it reads also steers it. A key in an environment variable is one shell command away from leaking (see “Prompt injection”).
  • A secrets manager doesn’t end the problem: to fetch a secret, the process needs another secret. That’s the “secret zero” problem: where the first credential comes from.

How SPIFFE works

ISSUING IDENTITY SPIRE server authority, entries ↕ mTLS: CSR → certificate SPIRE agent one per node ↕ socket: Workload API agent process harness CALLING A TOOL agent process → mTLS: authorization server (certificate → token) → mTLS + token: MCP server (own SVID, checks, decides)
  • SPIFFE is an open standard, and SPIRE is its most widely used implementation. A SPIFFE ID, such as spiffe://acme.example/agent/support, is an identity address in the trust domain acme.example, the area of one authority. An SVID is a signed proof of that ID: an X.509 certificate or a JWT. The Workload API is a local socket where a process fetches it. A bundle is the authority’s public keys, which anyone uses to check SVIDs. Below, “SPIRE agent” means the daemon and “agent” means the AI agent.
  • The SPIRE server is the authority. It holds the signing keys and the registration entries: rules saying “a process with these selectors on these nodes gets this ID”. It signs SVIDs.
  • The SPIRE agent runs on every node. It checks who is calling the socket and gives them only their own identity. It holds the SVIDs and keys of processes on that node.
  • The agent process holds its certificate, private key and bundle. On each connection it proves it has the key and checks the other side.
  • The authorization server checks the agent’s SVID and the user’s consent, then issues a token signed with its own key. The MCP server has its own SVID and bundle. It checks the certificate, the token and the policy, and makes the decision.
  • Node attestation. Before a SPIRE agent issues anything, the server has to trust it. The agent in turn checks the server with a bundle set by the operator. In Kubernetes it presents a signed service account token, and the server checks it through the TokenReview API. The agent gets its own SVID and talks to the server over mTLS from then on. The server sends it only the entries assigned to that node or its group. Secret zero therefore leaves the application and becomes platform configuration.
  • Workload attestation. The Workload API deliberately doesn’t authenticate the client directly. The SPIRE agent gets the caller’s PID from the kernel, reads the pod from its cgroup, and gets selectors from the kubelet, such as k8s:ns:prod and k8s:sa:support-agent. Every selector in the entry must match. No match returns PermissionDenied.
  • Keys. The SPIRE agent creates the process’s key pair and sends the server only a CSR, a public key with a request to sign it. The server signs the certificate with the authority’s key and doesn’t receive the process’s private key. The certificate waits in a cache until the process asks for it, and the SPIRE server takes no part in a tool call. A JWT-SVID has no process key pair: the server signs it with a separate JWT key.
  • Rotation. The SPIRE agent usually renews a certificate halfway through its life and pushes the new one down an open stream. The application has to reload it: a process that read its certificate once at startup stops working when it expires.
  • An MCP server and an authorization server in the same trust domain get the bundle from their own Workload API, and new keys down the same stream. A server outside the domain has no such socket: the domains then exchange bundles (federation), or an operator configures the bundle by hand. If the tool doesn’t know SPIFFE, only the OAuth token is left.
  • Security is a chain. The kernel gives a PID the process can’t forge, and the kubelet says which pod that is. The server checked the node, and the SPIRE agent issues only identities assigned to that node and matching the selectors. The authority’s signature lets you check a certificate with the bundle alone, without asking the SPIRE server. The TLS handshake proves possession of the private key. A certificate is public, so it proves nothing alone: the key is the proof, and the key is what you protect. The receiver must also check for the expected SPIFFE ID, because a valid signature only says “from this domain”.

Two identities in one call

  • A SPIFFE ID says which agent is calling, not who it works for. Without that second fact, a broadly privileged agent becomes a “confused deputy”: a user with no right to some data gets it through an agent that has the right. The decision has to see both identities, and the effective permissions are the intersection of what the agent and the user may do.
  • RFC 8693 separates impersonation from delegation. With impersonation, A appears as B and the logs don’t show A. With delegation, A keeps its own identity and the token names it in the act claim. You want delegation for agents, otherwise an audit can’t tell a human click from a model’s decision. In the authorization code flow shown above, the agent is in client_id, and act usually appears with token exchange.
  • The agent shouldn’t know the user’s password or hold a long-lived token. It gets a token for one server and scope, and proves its identity to the authorization server with its SVID.
  • A tool that calls another service doesn’t forward the token (MCP forbids this as token passthrough). It exchanges it for a new, narrower one.

Where it doesn’t protect you and when it pays off

  • mTLS stops eavesdropping, a certificate without its key, and impersonation, if you check the expected SPIFFE ID. It won’t stop key theft or code with access to the socket.
  • A TTL limits how long a stolen credential works. It won’t stop a live attack or a fresh fetch by a process with the socket.
  • aud stops a token being used at another service, if the receiver checks it. It won’t stop a replay at the same service.
  • cnf stops a token from a log being used without the key, if the server checks the binding. It won’t stop the key being stolen along with the token.
  • Node attestation stops a foreign daemon posing as a SPIRE agent. Workload attestation stops a process without matching selectors, but not one with the same selectors.
  • Policy in the tool stops a call outside the role and limits. It won’t stop a harmful call that fits the rules. It’s the only one of these protections that acts on a manipulated agent, because that agent has a valid SVID. Narrow permissions and human approval help too.
  • With an entry based on namespace and service account, attestation can’t tell a harness from the shell it started: both have the same selectors, and the caller picks the aud in FetchJWTSVID. If the model can run a command in a container with the Workload API socket, it gets the agent’s identity and a token for any service that accepts it. Executable path or hash selectors narrow the entry, but the container is a simpler boundary: the socket only beside the harness, and tool code in a separate sandbox with different selectors (see “The coding-agent harness”).
  • Cutting an agent off isn’t instant. Deleting the registration entry stops new SVIDs, but issued ones work until they expire. The SPIRE agent may keep working from cached entries for a moment, and credentials add up: a 5-minute JWT-SVID exchanged just before expiry for a 15-minute AWS session gives almost 20 minutes of access. Likewise, an open TLS connection lasts until the server caps it. The worst-case cut-off is the sum of the whole chain, so choose TTLs for it, not for convenience.
  • Replicas usually share one ID because they have the same selectors. A role ID with a session number in the logs is enough. A per-instance ID needs an entry per pod.
  • Selectors are trustworthy only for unprivileged processes. SPIRE’s documentation notes that root on the node can change cgroup membership. A seized node gives access to identities allowed there by registration entries, including identities shared with other nodes. If such an identity may obtain an intermediate CA or manage the SPIRE server, the whole domain is at risk. A seized SPIRE server means the whole domain.
  • An agent in one cloud: start with native workload identity, such as IAM roles for pods. You get short-lived credentials with no infrastructure of your own. SPIFFE pays off when agents and tools run across several clouds or clusters, or when you need one identity model across different systems.
  • SPIRE is a critical service: an outage blocks issuing and renewing SVIDs, and short TTLs leave little time to fix it. A coding agent on a laptop runs as you, so attestation adds little there. The sandbox and narrowly scoped tokens matter most.
  • As of October 2026, SPIFFE is a production standard, while the layer for agents is still forming. AIMS is an informational draft from the IETF’s WIMSE working group that composes existing standards and defines no protocol or MCP profile.
