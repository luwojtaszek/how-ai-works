Agent identity

An agent calling tools has to prove who it is, and a shared API key can’t do that: it only shows that someone holds the key. SPIFFE gives each process a short-lived identity issued from where and how it runs. It answers “who is calling”, but not “should they be”.

Why an API key isn’t an identity

  • A key is a bearer secret and doesn’t say who used it. When every agent replica and two other teams share the same key, the log only shows “key X”. Rotating it affects everyone at once, so rotation gets postponed and the key lives for months.
  • An agent is a worse keeper of secrets than an ordinary service, because the content it reads also steers it. A key in an environment variable is one shell command away from leaking (see “Prompt injection”). The IETF AIMS draft (September 2026) calls static API keys an antipattern and requires that the LLM has no access to the agent’s credentials.
  • A secrets manager doesn’t end the problem: to fetch a secret, the process needs another secret. That’s the “secret zero” problem: where the first credential comes from.

How SPIFFE works

  • SPIFFE is an open standard with three parts. A SPIFFE ID is an identity address, such as spiffe://acme.example/agent/support. An SVID is a signed document proving that ID: an X.509 certificate or a JWT. The Workload API is a local endpoint where a process fetches its SVIDs and trust keys. SPIRE is the most widely used implementation: a server acts as the certificate authority, and an agent runs on every node. Below, “SPIRE agent” means that daemon and “agent” means the AI agent.
  • Secret zero disappears because the Workload API deliberately doesn’t authenticate the client directly. The SPIRE agent works out who is calling out of band: it gets the caller’s PID from the kernel, reads the pod from its cgroup, and gets selectors from the kubelet, such as k8s:ns:prod and k8s:sa:support-agent. A registration entry says which selectors a process needs to receive a given ID. No match returns PermissionDenied.
  • The workload.spiffe.io: true header isn’t a password. It guards against SSRF, because an attacker forcing a request through a service usually can’t control gRPC metadata.
  • SPIRE’s default TTL is 1 h for an X.509-SVID and 5 min for a JWT-SVID. The SPIRE agent usually renews a certificate halfway through its life and pushes the new one down an open stream, with no process restart. The application still has to reload it: a process that read its certificate once at startup stops working when it expires.
  • An X.509-SVID gives you mTLS: each side proves it holds the private key, so an intercepted certificate without the key is useless. A JWT-SVID passes through HTTP proxies but is a bearer token. The specification warns about replay and recommends a single aud value and the shortest practical lifetime.

Two identities in one call

  • A SPIFFE ID says which agent is calling, not who it works for. Without that second fact, a broadly privileged agent becomes a “confused deputy”: a user with no right to some data gets it through an agent that has the right. The decision has to see both identities, and the effective permissions are the intersection of what the agent and the user may do.
  • RFC 8693 separates impersonation from delegation. With impersonation, A appears as B and the logs don’t show A. With delegation, A keeps its own identity and the token names it in the act claim. You want delegation for agents, otherwise an audit can’t tell a human click from a model’s decision.
  • The agent shouldn’t know the user’s password or hold a long-lived token. It gets a token for one server and scope, and proves its identity to the authorization server with its SVID. The IETF draft oauth-spiffe-client-auth covers both options: a JWT-SVID as a client assertion and an X.509-SVID over mTLS. A certificate-bound token (RFC 8705) carries the certificate’s hash in cnf, so it’s useless without the private key.
  • A tool that calls another service doesn’t forward the token (AIMS calls this an antipattern, and MCP forbids it as token passthrough). It exchanges it for a new, narrower one. Multi-hop chains of agent, subagent and tool are still open work: the WIMSE group has several competing individual drafts.
  • The agent reaches the cloud without keys: a JWT-SVID with an AWS aud goes to sts:AssumeRoleWithWebIdentity, AWS checks the signature through a public OIDC Discovery Provider, and a condition on the role compares sub with the SPIFFE ID. The agent gets temporary AWS credentials back.

Where it doesn’t protect you and when it pays off

  • Identity describes a process, not an intent. A manipulated agent has a valid SVID and makes a valid call. Scope limits, policy on the tool side and human approval protect against that. AIMS adds that a local confirmation prompt in the agent’s app isn’t sufficient authorization, and treats observability as a security control.
  • With an entry based on namespace and service account, attestation can’t tell a harness from the shell it started: both have the same selectors, and the caller picks the aud in FetchJWTSVID. If the model can run a command in a container with the Workload API socket, it gets the agent’s identity and a token for any service that accepts it. Executable path or hash selectors narrow the entry, but the container is a simpler boundary: the socket only beside the harness, and tool code in a separate sandbox with different selectors (see “The coding-agent harness”).
  • Cutting an agent off isn’t instant. Deleting the registration entry stops new SVIDs, but issued ones work until they expire. The SPIRE agent may keep working from cached entries for a moment, and credentials add up: a 5-minute JWT-SVID exchanged just before expiry for a 15-minute AWS session gives almost 20 minutes of access. Likewise, an open TLS connection lasts until the server caps it. The worst-case cut-off is the sum of the whole chain, so choose TTLs for it, not for convenience.
  • Replicas usually share one ID because they have the same selectors. A per-instance ID needs an entry per pod, for example with the k8s:pod-uid selector, and a controller to create and delete those entries. The cheaper option is one ID per agent role with a session number in the logs. Policy works on roles anyway.
  • Selectors are trustworthy only for unprivileged processes. SPIRE’s documentation notes that root on the node can change cgroup membership. A compromised node means access to every identity that node can issue.
  • An agent in one cloud: start with native workload identity, such as IAM roles for pods. You get short-lived credentials with no infrastructure of your own. SPIFFE pays off when agents and tools run across several clouds or clusters, or when you need one identity model across different systems.
  • SPIRE is a critical service: an outage blocks issuing and renewing SVIDs, and short TTLs leave little time to fix it. A coding agent on a laptop runs as you, so attestation adds little there. The sandbox and narrowly scoped tokens matter most.
  • As of October 2026, SPIFFE is a production standard, while the layer for agents is still forming. AIMS is an informational WIMSE draft that composes existing standards and defines no protocol or MCP profile. Draft names and details may change.
