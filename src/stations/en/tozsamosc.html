Agent identity

Services an agent calls need to know who sent each request. A shared API key can’t tell them: anyone can copy it and use it for months. SPIFFE is an open standard that lets you replace it with a short-lived credential, issued automatically based on where and how the process runs.

Why agents need SPIFFE

  • Shared keys. An API key works like a password: knowing it is enough. If every agent replica and two other teams share a key, the log only shows “key X”. Changing it affects everyone, so it gets postponed and the key works for months.
  • Leak risk. Content an agent reads can influence its behaviour, so one shell command may expose a key in an environment variable (see “Prompt injection”). An agent calling many systems may hold several such keys.
  • First secret. A secrets manager can’t solve this: fetching a secret requires another secret. That’s the “secret zero” problem: where the first credential comes from.
  • SPIFFE credentials. A process starts without a secret and asks a local service for a credential. The service identifies it using system data. In SPIRE the credential lasts an hour or 5 minutes by default, and the process fetches a replacement before it expires.
  • What you gain. The application’s configuration contains no long-lived secret, and a stolen credential expires quickly. Each agent role can have its own identity for logging and policy, so you can block one role without affecting the others.
  • Limits. SPIFFE identifies the caller but doesn’t decide whether a call is allowed. A manipulated agent has a genuine identity, and a compromised process can fetch new credentials. You need narrow permissions, isolation and human approval.

How SPIFFE works

Step from a SPIRE entry to the MCP server’s decision. Highlights show who is communicating at each step

Messages are shortened; names and values are examples. This combines existing standards for services in your own trust domain. It isn’t a ready-made profile: MCP doesn’t specify mTLS or SPIFFE, and your authorization server must support certificate-bound tokens.

  • SPIFFE is an open standard; SPIRE is its most widely used implementation. A SPIFFE ID, such as spiffe://acme.example/agent/support, names an identity in the trust domain acme.example, under one certificate authority (CA). An SVID is a signed credential for that ID: an X.509 certificate or JWT. A process fetches it through the local Workload API socket. The domain’s public keys form a bundle used to verify SVIDs. Below, “SPIRE agent” means the service on a node and “agent” means the AI agent.
  • The SPIRE server acts as the CA and signs SVIDs. It holds the signing keys and registration entries: rules specifying which processes on which nodes receive each ID.
  • The SPIRE agent runs on every node. It identifies the caller at the socket and issues only that process’s SVIDs. It holds SVIDs and keys for processes on the node.
  • The agent process holds its certificate, private key and bundle. On each connection it proves it has the key and checks the other side.
  • The authorization server verifies the agent’s SVID and the user’s consent, then issues a token signed with its own key. The MCP server has its own SVID and bundle. It checks the certificate, token and access policy before deciding.
  • Node attestation. Before a SPIRE agent issues anything, the server must trust it. The SPIRE agent verifies the server using a bundle from the operator. In Kubernetes it presents a signed service account token, which the server checks through the TokenReview API. The SPIRE agent receives its own SVID and connects to the server over mTLS. It receives only entries for its node or group. This moves secret zero from the application to platform configuration.
  • Workload attestation. The Workload API deliberately doesn’t authenticate clients directly. The SPIRE agent gets the caller’s PID from the kernel, identifies its pod via cgroup, and gets selectors from the kubelet, such as k8s:ns:prod and k8s:sa:support-agent. All entry selectors must match or the process receives PermissionDenied.
  • Keys. The SPIRE agent creates the process’s key pair and sends only a CSR, a public key with a signing request, to the server. The server signs the certificate with the CA’s key and doesn’t receive the process’s private key. The certificate stays cached until the process fetches it; the SPIRE server isn’t involved in tool calls. A JWT-SVID has no process key pair: the server signs it with a separate JWT key.
  • Renewal. The SPIRE agent usually renews a certificate halfway through its validity and sends it over an open stream. The application must reload it. If it reads the certificate only at startup, it stops working when the certificate expires.
  • MCP and authorization servers in the same trust domain fetch the bundle through their own Workload API and receive new keys over the same stream. Servers outside the domain lack that socket, so domains exchange bundles (federation) or an operator configures them manually. Tools without SPIFFE support use only the OAuth token.
  • How trust is established. The kernel supplies a PID the process can’t forge, and the kubelet identifies the pod. The server has verified the node. The SPIRE agent issues only identities assigned to that node and matching the selectors. The CA’s signature lets the receiver verify a certificate using the bundle, without contacting the SPIRE server. The TLS handshake proves possession of the private key. The certificate is public and proves nothing on its own, so protect the key. The receiver must also check the expected SPIFFE ID: a valid signature confirms only the domain.

Agent and user identity

  • A SPIFFE ID identifies the agent, but not the user it works for. Without that information, a broadly privileged agent can become a “confused deputy”: a user obtains data they can’t access through an agent that can. Access decisions must account for both identities and allow only what both the agent and user may do.
  • RFC 8693 distinguishes impersonation from delegation. With impersonation, A acts as B and doesn’t appear in the logs. With delegation, A keeps its identity in the token’s act claim. Agents need delegation so an audit can distinguish a human click from a model’s decision. In the authorization code flow above, client_id identifies the agent; act usually appears with token exchange.
  • The agent shouldn’t know the user’s password or hold their long-lived token. It gets a token for one server and scope, and authenticates to the authorization server with its SVID.
  • A tool calling another service exchanges the token for a new, narrower one. MCP forbids forwarding it (token passthrough).

Limits and uses

  • mTLS prevents eavesdropping, certificate use without its key, and impersonation if you check the expected SPIFFE ID. It won’t stop key theft or code with socket access.
  • TTL limits stolen credential use. It won’t stop an attack in progress or a process fetching replacements via the socket.
  • Checking aud prevents token use at another service. The token can still be replayed at the same service.
  • Checking cnf blocks use of a logged token without its private key. Stealing both bypasses this protection.
  • Node attestation blocks a service posing as a SPIRE agent. Workload attestation rejects processes without matching selectors, but admits any with the same selectors.
  • The tool’s policy blocks calls outside the role and limits, but allows harmful calls that meet its rules. Of these checks, only policy constrains a manipulated agent, whose SVID is valid. Narrow permissions and human approval also help.
  • An entry based on namespace and service account can’t distinguish a harness from a shell it starts: both processes have the same selectors, and the caller chooses aud in FetchJWTSVID. If the model can run commands in a container with the Workload API socket, it can obtain the agent’s identity and a token for any service that accepts it. Executable path or hash selectors narrow the entry, but separating containers is simpler: keep the socket with the harness and run tool code in a separate sandbox with different selectors (see “The coding-agent harness”).
  • Blocking an agent takes time. Deleting its registration entry stops new SVIDs, but existing ones work until expiry, and the SPIRE agent may briefly use cached entries. Lifetimes add up: a 5-minute JWT-SVID exchanged just before expiry for a 15-minute AWS session gives almost 20 minutes of access. An open TLS connection also lasts until the server limits it. Set TTLs for the longest combined access time across the chain.
  • Replicas usually share an ID because they have the same selectors. A role ID and session number are enough for logs. An instance ID requires an entry for each pod.
  • Selectors are trustworthy only for unprivileged processes: SPIRE’s documentation says root on a node can change cgroup membership. A compromised node exposes identities allowed there by registration entries, including those shared with other nodes. If any can obtain an intermediate CA or manage the SPIRE server, the whole domain is at risk. Compromising the SPIRE server also endangers the whole domain.
  • In one cloud, start with its native workload identity, such as IAM roles for pods. These provide short-lived credentials without extra infrastructure. SPIFFE pays off when agents and tools span several clouds or clusters, or different systems need a shared identity model.
  • SPIRE is a critical service: an outage blocks issuing and renewing SVIDs, and short TTLs leave little repair time. A laptop coding agent runs under your account, so attestation adds little. A sandbox and narrowly scoped tokens matter most.
  • As of October 2026, SPIFFE is used in production, but standards for agents are still emerging. AIMS, an informational draft from the IETF’s WIMSE working group, combines existing standards. It defines no protocol or MCP profile.
