From chat to GPU

Before the model answers a chat message, the request passes through a gateway, an inference server, the model, libraries, a driver and the GPU. Each level has its own job and knows little about the others.

When an answer arrives slowly or the server runs out of memory, the API alone doesn’t reveal the cause. Dividing the stack into levels shows which component to inspect.

The return path: from logits to text

  • A token may hold only part of a UTF-8 character, so the decoder waits for enough tokens to complete it.
  • An agent’s new request passes through all the levels again (see “The agent loop”).

Reasoning and the reasoning effort setting

  • Reasoning has no level of its own. To the inference server it is ordinary tokens, and to CUDA ordinary matrix multiplication. Whether the model generates another reasoning token depends on the prompt, the tokens so far and its weights. Some open reasoning models generate these tokens between start-of-thinking and end-of-thinking markers.
  • Reasoning effort is an API parameter. In open models the chat template can turn it into a few tokens in the prompt, and the server can also limit reasoning length. It depends on the model. A server-side parser separates reasoning tokens from the answer. In closed models the details aren’t public (see “Reasoning models”).
  • Higher effort doesn’t give the model an extra GPU. The conversation occupies its batch slot and KV cache memory for longer.

What goes in the container image and what stays on the host

  • The container image holds vLLM, PyTorch and CUDA libraries, including cuBLAS and the runtime. The full CUDA Toolkit is for building software, so a node that only runs models usually doesn’t need it.
  • The driver’s kernel module runs in the host kernel, which the container shares. The NVIDIA Container Toolkit exposes driver libraries, including libcuda.so, and the /dev/nvidia* devices to the container. So the driver must be new enough for the CUDA libraries in the image. If you get an “insufficient driver” error, compare the driver version on the host with the CUDA version in the image before touching your code.
  • The NVIDIA Device Plugin reports the nvidia.com/gpu resource to the kubelet, and the cluster scheduler places a pod with that limit on a node with free GPUs. The GPU Operator installs these components automatically.
  • Three replicas hold three full copies of the weights and increase throughput. Tensor parallelism splits one copy’s weights and computation across several GPUs, usually because the model doesn’t fit on one.

What this means when you build a system

  • Use the symptom to narrow down the level. A long time to first token under load usually means the queue or prefill, level 3. When memory runs out, check the logs for what failed to allocate: weights, working buffers or CUDA Graphs. Under KV cache pressure, vLLM usually pauses conversations and recomputes their cached state; fewer concurrent conversations help. A quality drop after switching inference servers often comes from a changed template or sampler settings.
  • You can switch inference servers without changing the weights if the new one supports the model’s architecture and format: vLLM, SGLang, TensorRT-LLM or llama.cpp. Speed and memory use can differ a lot on identical weights, so compare them on your own traffic (see “Open-weight models”).
  • Lower levels depend on the hardware. Instead of CUDA and the NVIDIA driver, AMD GPUs use ROCm, Macs use Metal and TPUs use the XLA compiler. Levels 1–4 look similar; levels 5–7 change.
