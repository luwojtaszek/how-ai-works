The inference stack

Before the model answers a chat message, the request passes through a gateway, an inference server, the model, libraries, a driver and the GPU. Each level has its own job and knows little about the others.

When an answer arrives slowly or the server runs out of memory, the API alone doesn’t reveal the cause. Dividing the stack into levels shows which component to inspect.

Step through generating an answer. Tap an element for details

Example stack: Kubernetes, vLLM, PyTorch and an NVIDIA H100. The example model has 70 billion parameters and 80 layers. GPU figures are H100 specifications; the model, replica count, token IDs and tensor shapes are illustrative and simplified. OpenAI and Anthropic don’t publish their full stacks.

Level 1. System: steps 1 and 23

  • History. At step 1 the application sends the whole history and keeps the connection open until the final event. Between messages the history lives in the application, and an idle chat reserves no GPU memory.
  • The way back. At step 23 text arrives in fragments as tokens are picked. A tool call in the answer means a new request, which passes through all the levels again (see “The agent loop”).

Level 2. Cluster: steps 2 and 3

  • The request. The gateway checks the key and limits, and the router picks one replica. A plain Service doesn’t look at the prompt. A prefix-aware router (llm-d, NVIDIA Dynamo) can pick a replica that still holds this conversation’s blocks, weighing that against load.
  • Why a replica has four GPUs. The example model has 70 billion parameters, 140 GB of weights, and one H100 has 80 GB of memory. So one copy of the model must span several GPUs, as level 7 explains. Three replicas are three independent copies, each with its own KV cache.
  • Placement. Before requests arrive, Kubernetes places the pod on a node with free GPUs. The pod asks for nvidia.com/gpu: 4, and the NVIDIA Device Plugin reports only a count, nothing about how the GPUs are linked. A fast link between the four comes from the node’s design, or from a Dynamic Resource Allocation claim that selects devices by attributes.
  • Several nodes. A model too large for one node runs as a group of pods forming one replica. LeaderWorkerSet manages the group, Ray can coordinate the workers, and gang scheduling, when enabled, starts the pods together or not at all, because without any one of them the model can’t compute a token.

Level 3. Server: steps 4–9 and 20–22

  • Start. Before its first request, vLLM loads the weights, measures working buffers and CUDA Graphs, and gives the rest of its GPU memory budget (92% by default, gpu_memory_utilization) to the KV cache. In the example four H100s give 320 GB, and about 140 GB remain after weights and buffers.
  • Arrival. Steps 4–6 apply the chat template, tokenise the messages and put the request in the replica’s queue.
  • Model pass. One run of all the layers for the whole batch, a group of conversations processed together. Before each pass (step 7) the scheduler gives a block to every running conversation that needs one, then admits waiting requests while free blocks and limits last (max_num_seqs, max_num_batched_tokens). The rest wait, which is why open chats can far outnumber conversations being computed.
  • Prefill and decode. Prefill computes the prompt’s KV cache, sometimes across several passes, and the last one allows the first output token to be picked. Decode processes the last picked token to pick the next. One batch can mix decode of running conversations with a prefill chunk of a new one.
  • Blocks. The KV cache manager divides this memory into blocks of 16 tokens, 5.2 MB each in the example. It hands them to a conversation as it grows and keeps its block table, so one conversation’s blocks can sit anywhere in memory (PagedAttention). A finished conversation returns them at once.
  • Prefix cache. A freed full block keeps its contents and a hash of the tokens from the start of the prompt to its end. A request with the same start gets it as already computed and skips its prefill, and the blocks unused longest are overwritten first. That’s why the next turn of a chat can be cheap (see “Prompt caching”).
  • Running out. When free blocks run out mid-generation, the scheduler pauses a conversation, usually the most recently admitted, and frees its blocks. On resume vLLM V1 recomputes the missing cache by default, and the user sees the stream stall.
  • The way back. Steps 20–22 pick tokens, check stop conditions and send text as SSE events. An incomplete UTF-8 character waits for the next token. If generation isn’t finished, the loop returns to step 7.
  • Reasoning. To the server these are ordinary tokens, and a parser separates them from the answer. Higher reasoning effort gives no extra GPU: the conversation holds its blocks and batch slot for longer (see “Reasoning models”).

Level 4. Model: steps 10, 11 and 19

  • Shared weights. In decode one pass gives every conversation in the batch one new token. The weights are read once per pass for the whole batch, so eight conversations cost the same weight reads as one. That is the point of a batch. Each conversation’s KV cache is separate.
  • One conversation’s cache. Every layer keeps the key and value of every token for each KV head. In the example: 2 × 80 layers × 8 heads × 128 numbers × 2 bytes = 0.33 MB per token, 10.5 GB for 32,000 tokens. Without grouped-query attention, with 64 KV heads, it would be 84 GB, more than one H100 has. Formula and real models are in “The generation loop and KV cache”.
  • How many conversations fit. 140 GB of cache is about 430,000 tokens: 13 conversations of 32,000 tokens, or proportionally more shorter ones. The scheduler’s limits from level 3 also cap conversations computed at once.

Level 5. Libraries: steps 12–14

  • Execution. Model layers become GPU kernel launches: matrix multiplication from cuBLAS, attention from FlashAttention. Compilation can fuse operations, and a CUDA Graph replays recorded work with one call, so the CPU doesn’t submit each kernel separately. The GPU still runs them all.
  • Memory. The KV cache is a PyTorch tensor prepared at start. PyTorch’s allocator keeps the memory it got from the driver, so nvidia-smi shows the reservation, not current use. The block assignments from level 3 happen inside this tensor, without the lower levels.
  • Other hardware. Levels 5–7 depend on the hardware: AMD GPUs use ROCm, Macs use Metal and TPUs use the XLA compiler.

Level 6. Driver: steps 15 and 16

  • Resources. The driver in the host kernel creates GPU channels and maps memory into the process at start and on allocations. Reusing a KV block needs no new mapping.
  • Submitting work. After that a kernel launch is a write to a command buffer and to the doorbell, with no system call. That’s why repeated launches don’t load the Linux kernel.
  • Image and host. vLLM, PyTorch, cuBLAS and the CUDA runtime come from the container image; libcuda.so and the kernel module come from the host through the NVIDIA Container Toolkit. The host driver must be new enough for the CUDA version in the image.

Level 7. GPU: steps 17 and 18

  • Tensor parallelism. It splits one layer across GPUs: each weight matrix is cut into four parts, and each GPU holds 2 of the 8 KV heads. A conversation of 32,000 tokens therefore takes about 2.6 GB on each of the four GPUs. No GPU has a layer’s full result, so they must compute it together.
  • Why fast links are required. In the classic layout GPUs add up partial results (all-reduce) twice in every layer, 160 times per pass with 80 layers, and all four wait for each exchange. In decode one exchange is small, 8 tokens × 8192 numbers × 2 bytes = 131 KB, so latency matters. In a 32,000-token prefill one exchange is 524 MB, about 84 GB per pass, so bandwidth matters. Illustrative numbers.
  • NVLink and the network. H100 NVLink gives 900 GB/s in total, about 450 GB/s each way. A 400 Gb/s network port (InfiniBand or RoCE) gives 50 GB/s each way, even with RDMA writing straight into GPU memory. Those 84 GB take about 0.2 s on NVLink and about 2 s on one port, and these are interface limits, before overhead. So a tensor-parallel group stays inside one NVLink domain.
  • Pipeline parallelism. It splits the model into groups of layers, one per node, each with its own weights and cache. One handover crosses between stages instead of 160 exchanges, so a network is enough. The price is latency, because a token passes the stages in turn, although several batches at different stages can raise throughput. vLLM’s rule: tensor parallelism equal to the GPUs in a node, pipeline parallelism equal to the number of nodes.
