# Working on "How AI works" / "Jak działa AI"

An interactive, bilingual guide for engineers: how language models work under the hood and what matters when building agentic systems. English is the default at `/`, Polish lives under `/pl/`. The bar is simple: the content should be good enough that engineers recommend it to each other.

## Structure

| What | Where |
|---|---|
| Topic page text (Polish, English) | `src/stations/<id>.html`, `src/stations/en/<id>.html` |
| Order, chapters, self-check, follow-ups, sources, search titles (Polish / English) | `src/data.js`, `src/data.en.js` |
| English URL slug per topic | `SLUG_EN` in `src/data.en.js` (Polish pages use the id) |
| "How this guide is made" | `src/components/AboutPage.astro` |
| Widgets | `src/scripts/app.js`, one `init…` function per topic, wired in the `inits` map; text via `tr('polski','English')` |
| What changed | `src/changelog.js` (drives the "What's new" page, RSS and "new" badges) |
| Styles | `src/styles/global.css`; topic-specific blocks between `/* <id> */` and `/* end <id> */` |
| Social preview images | `public/og/<lang>/<id>.png`, generated by `scripts/og.sh` |
| Real model data for widgets | `src/scripts/tokens-data.json` (`scripts/gen-tokens.py`), `src/scripts/model-data.json` (`scripts/gen-model-data.py`); usage in each script's first line |

The layout adds breadcrumbs, the "In plain words" box (`X[id].lay`), "Check yourself" (`ST[id]` / `ST_EN[id]` question and short answer, `X[id].f` follow-ups), sources (`X[id].r`), prev/next and the updated date. Never write those inside a station file.

## Adding or updating a topic

1. Polish station `src/stations/<id>.html`: `<h2>` title, `<p class="lede">`, widget(s) in `<div class="lab">`, then 2–4 sections as `<h3 class="sub">` + `<ul class="notes">`.
2. English station `src/stations/en/<id>.html` with identical markup (same ids and classes); translate, don't transliterate.
3. Data: `ST.<id>` and `X.<id>` in `src/data.js`, `ST_EN.<id>` and `X_EN.<id>` in `src/data.en.js`; `ht` in `X`/`X_EN` is the search title (what people type into Google, ≤ ~60 chars). For a new topic add the id to a chapter in `GROUPS` and an English slug to `SLUG_EN`. Never change a published slug.
4. Widget: an `init…` function in `src/scripts/app.js` added to `inits`; every visible string through `tr()`; colours only via CSS variables so light and dark both work.
5. Changelog: add an entry at the top of `src/changelog.js` (`added` for new topics, `updated` for meaningful changes, text in both languages).
6. New or renamed topic: run `scripts/og.sh` to regenerate the preview images.
7. Check: `bun run build`, then `scripts/qa.sh <id>` (both languages, phone and desktop). Look at the page yourself on a phone width.

## Content standard

- Lede: the essence in 1–2 sentences. Then an analogy that genuinely helps, the widget, and sections from mechanism to nuances to what it means for building systems.
- Every sentence teaches something concrete: a mechanism, number, trade-off, failure mode or decision rule. No filler, no marketing tone, no emoji.
- Correct as of the date you write it. Numbers with units and context; dates for anything time-sensitive; primary sources you actually opened (2–4 per topic). Illustrative numbers in widgets are labelled as illustrative.
- Cross-reference other topics by their exact title in quotes.
- "Check yourself" is a self-check, not interview prep: don't frame the guide around job interviews. Short answers and follow-ups are written in the second person or impersonally, never "I…".
- Vendor-specific content (for example Jev / System One) separates the vendor's claims from general facts.

## Keeping facts fresh

Every quarter and after a major model or API release, list the dated and versioned claims and recheck the ones that may have moved:

```sh
grep -rnE "as of|stan na|(January|February|March|April|May|June|July|August|September|October|November|December) 20[0-9]{2}|20[0-9]{2}-[0-9]{2}-[0-9]{2}" src/stations src/data.js src/data.en.js
```

Record real corrections in the changelog (`updated`).

## Automated maintenance

- `.github/workflows/freshness.yml`: on the 1st of every month Claude Code rechecks dated claims against primary sources and opens a pull request with the fixes. Run it by hand (Actions → Freshness → Run workflow) with a task such as "Add a topic on <X>".
- `.github/workflows/claude.yml`: mention `@claude` in an issue or pull request comment (write access only), for example on an error report.
- Both need the repository secret `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`). CI has no browser, so pull requests from CI skip `scripts/og.sh` and `scripts/qa.sh`: new topics fall back to the site preview image until `scripts/og.sh` is run locally.

## Deploy

Every push to `main` builds the site, checks internal links and publishes it to GitHub Pages (`.github/workflows/deploy.yml`). The public address is `site` in `astro.config.mjs`.
